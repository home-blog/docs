# 07. 브랜치 전략 (Git Flow)

> 2026-10-13 사용자 결정. 코드 저장소 `home-blog/blog`에 적용 (코드 PR #53).

## 한 줄 요약

**`main`은 "지금 서비스에 올라가 있는 코드", `develop`은 "다음에 올라갈 코드"를 모으는 곳이다.** 새 일은 언제나 `develop`에서 가지를 쳐서 PR로 돌아오고, 배포할 때만 `main`으로 간다.

## 비유: 출판사

| 브랜치 | 출판사로 치면 | 하는 일 |
|---|---|---|
| `main` | 서점에 깔린 책 | 배포된 코드. 릴리스마다 태그(`v0.4.0`)를 붙인다 |
| `develop` | 편집부 책상 위 원고 | 다음 판에 들어갈 글이 모인다. 기본 브랜치 |
| `feature/<내용>` | 작가 한 명의 원고 | 기능 하나. `develop`에서 만들고 `develop`으로 돌아온다 |
| `release/<번호>` | 인쇄 직전 교정쇄 | 다음 판의 마지막 확인(날짜, 버전 번호, 바뀐 것 기록). `main`에 합치면 배포 |
| `hotfix/<번호>` | 이미 나간 책의 정오표 | 서비스가 멈추는 급한 버그만. `main`에서 만들고 `main`과 `develop` 둘 다에 넣는다 |

## 흐름

```text
           feature/v0.5-social-login ─┐
           feature/글쓰기-임시저장 ────┤ PR
                                      ▼
develop ──●────────●────────●─────────●─────────────────●──▶
           \                           \               ▲
            \                           release/0.5.0  │ main을 다시 합침
             \                               │ PR      │
main ─────────●(v0.4.0)──────────────────────●(v0.5.0)─┴──▶
                                             │
                                  Actions "배포" 0.5.0 → 태그·릴리스 노트
```

1. **기능**: `develop`에서 `feature/<내용>`을 만든다 → 커밋을 쌓는다 → `develop`으로 PR → CI·CodeRabbit·SonarQube 통과 → 합친다. 바뀐 것은 `CHANGELOG.md`의 `준비 중` 절에 적는다.
2. **릴리스**: 사용자가 화면을 확인하고 "배포해줘" → `develop`에서 `release/0.5.0`을 만든다 → CHANGELOG의 `준비 중`을 날짜로 바꾸고 버전 번호를 확인한다 → `main`으로 PR → 합친다 → Actions `배포`에 `0.5.0`을 넣어 돌린다 → 태그 `v0.5.0`과 GitHub 릴리스가 생긴다 → `main`을 `develop`에 다시 합친다.
3. **급한 수정**: `main`에서 `hotfix/0.5.1` → 고치고 CHANGELOG에 `0.5.1` 절 → `main`으로 PR·배포 → `develop`에도 합친다.

## 왜 이렇게 하나

- **배포본이 항상 깨끗하다**: `main`에는 확인을 마친 릴리스만 들어간다. 무엇이 서비스에 올라가 있는지 `main`과 태그만 보면 안다.
- **급한 수정이 쉽다**: `develop`에 다음 기능이 반쯤 들어가 있어도, `main`에서 바로 `hotfix`를 만들어 그 버그만 고쳐 낼 수 있다.
- **여럿이 동시에 일해도 덜 부딪힌다**: 기능마다 가지가 따로 있고, 합치는 곳(`develop`)이 하나다.

## 규칙

- `main`과 `develop`에는 직접 올리지 않는다. 언제나 PR로 합친다.
- 브랜치 이름: `feature/`, `release/`, `hotfix/` + 내용이나 번호. (설정만 바꾸는 일은 `chore/`도 쓴다)
- PR은 기능 단위로 묶어서 적게 (2026-10-12 사용자). 리뷰 수정은 같은 PR에서.
- 버전 번호: 기능이 들어가면 가운데 숫자(0.5.0), 급한 수정만이면 끝 숫자(0.5.1). API 주소 버전(`/api/v1`)은 따로 간다 ([06](06-API-버전과-릴리스.md)).

## GitHub 설정 (저장소 관리자가 한다)

- Settings → General → **Default branch**를 `develop`으로.
- Settings → Rules(또는 Branches) → `main`, `develop`에 보호 규칙: PR로만 합치기, CI(서버·화면) 통과 필수, 강제 push·삭제 막기.
