# Feature Specification: 공지사항 (v0.6.0)

**Feature**: `012-notices` · **Created**: 2026-10-15 · **Status**: 구현 중

**요청**: [`다음-기능.md`](../../docs/2-요구사항/다음-기능.md) N-24 (2026-10-13 사용자 추가: "관리자를 따로 만들지는 않았지만 넣어야겠지", 업데이트 글은 "추천대로").

이 문서는 **무엇을**만 적습니다. 방법은 [research.md](research.md), [data-model.md](data-model.md), [contracts/notice-api.md](contracts/notice-api.md)에 있습니다.

## 쉬운 설명

사이트 안에 **공지사항 게시판**이 생깁니다. 서비스가 바뀐 소식(**업데이트**)과 점검 안내 같은 **공지**를 한곳에서 봅니다. 글은 **관리자**만 씁니다. 관리자는 회원 가운데 지정한 사람입니다.

## 사용자 이야기

### US1 공지사항 보기 (P1)
누구나(로그인하지 않아도) `/notices`에서 공지사항 목록을 봅니다.

1. 탭은 **전체 / 업데이트 / 공지**입니다. 탭을 바꾸면 주소에 남아 새로고침해도 그 탭입니다.
2. 글마다 종류 **꼬리표**가 붙습니다. 업데이트는 초록 꼬리표, 공지는 노란 형광펜 꼬리표이고, 색만으로 구분하지 않도록 꼬리표에 "업데이트"·"공지" 글자를 함께 씁니다.
3. **고정**한 글은 탭 안에서 맨 위에 "고정" 표시와 함께 나오고, 나머지는 새 글부터 나옵니다.
4. 업데이트 글에는 릴리스 번호(예: v0.6.0)가 보입니다.
5. 한 쪽에 10개씩 나오고 아래에 쪽 번호가 있습니다.
6. 글이 없으면 빈 원고지와 "아직 공지사항이 없습니다"가 보입니다.

**받아들이는 기준**
- S1-1 로그인하지 않은 방문자가 `/notices`를 열면 목록이 보인다.
- S1-2 "업데이트" 탭에서는 업데이트 글만, "공지" 탭에서는 공지 글만 보인다.
- S1-3 고정 글 2개와 보통 글 3개가 있으면 고정 2개(새 것 먼저)가 위, 보통 3개(새 것 먼저)가 아래에 온다.
- S1-4 글이 11개면 1쪽에 10개, 2쪽에 1개.
- S1-5 없는 종류(`?kind=xyz`)를 넣으면 전체로 본다. 쪽 번호 규칙은 글 목록(004 D-2)과 같다.

### US2 공지사항 읽기 (P1)
목록에서 글을 누르면 `/notices/{번호}`에서 본문을 읽습니다.

1. 본문은 글과 같은 마크다운이고, HTML은 글자 그대로 보입니다.
2. 업데이트 글에는 **"자세한 변경 기록"** 링크가 있어 그 번호의 GitHub 릴리스로 갑니다.
3. 없는 번호는 "찾을 수 없습니다" 화면입니다.

**받아들이는 기준**
- S2-1 업데이트 글(v0.6.0)을 열면 본문과 `v0.6.0` GitHub 릴리스 링크가 보인다.
- S2-2 공지 글에는 릴리스 링크가 없다.
- S2-3 없는 번호는 404.

### US3 새 공지 알림 (P2)
1. 머리글에 "공지" 링크가 있고, **마지막으로 공지사항을 본 뒤 새 글이 올라왔으면** 작은 점이 붙습니다. 공지사항 목록을 열면 점이 사라집니다.
2. 처음 오는 방문자에게는 점을 띄우지 않습니다(모든 글이 새 글이라 의미가 없어서).
3. 바닥글에 "공지사항" 링크가 있습니다.

**받아들이는 기준**
- S3-1 목록을 본 뒤 관리자가 새 글을 쓰면 머리글 "공지"에 점이 보인다.
- S3-2 목록을 열면 점이 사라진다.
- S3-3 이 기기에서 공지사항을 한 번도 보지 않았으면 점이 없다.

### US4 관리자가 공지사항 쓰기·고치기·지우기 (P1)
관리자만 글을 씁니다.

1. 관리자에게만 목록에 **"글쓰기"**, 읽기 화면에 **"수정"·"삭제"** 가 보입니다.
2. 쓰는 칸: 종류(업데이트/공지), 제목(1~100자), 본문(1~10,000자, 마크다운), 릴리스 번호(업데이트일 때만, `0.6.0` 모양), 고정 여부.
3. 업데이트 글은 릴리스 번호가 꼭 있어야 하고, 공지 글에는 릴리스 번호를 넣을 수 없습니다.
4. 삭제는 확인 창을 거칩니다. 지운 글은 다시 볼 수 없습니다.
5. 관리자가 아닌 회원이 쓰기 주소를 직접 부르면 "권한이 없습니다"(403), 로그인하지 않았으면 로그인 요청(401)입니다.

**받아들이는 기준**
- S4-1 관리자가 업데이트 글(번호 0.6.0, 고정)을 쓰면 목록 맨 위에 보인다.
- S4-2 제목이 비었거나 101자면 칸 아래에 이유가 보이고 저장되지 않는다. 100자는 된다.
- S4-3 업데이트인데 번호가 없거나 `v0.6`·`0.6.0.1`·`abc` 같은 모양이면 거절. `0.6.0`, `0.10.12`는 된다.
- S4-4 공지에 번호를 넣으면 거절.
- S4-5 일반 회원이 쓰기·수정·삭제를 부르면 403, 로그인하지 않았으면 401.
- S4-6 관리자가 글을 지우면 목록과 읽기에서 사라진다(404).
- S4-7 탈퇴한 관리자 계정은 쓸 수 없다(401).

### US5 관리자 정하기 (P1)
1. 관리자는 회원 표에서 정합니다. 화면으로 관리자를 만들거나 바꾸는 기능은 **두지 않습니다**(운영자가 DB에서 한 번).
2. 로그인 상태 확인(`/auth/me`)이 관리자인지 함께 알려 주어 화면이 관리자 버튼을 보입니다.
3. 관리자에서 빼면 **다음 요청부터** 바로 쓸 수 없습니다(다시 로그인하지 않아도).

**받아들이는 기준**
- S5-1 회원을 관리자로 바꾸면 `/auth/me`에 관리자 표시가 생긴다.
- S5-2 관리자에서 뺀 뒤 쓰기를 부르면 403.

## 업데이트 글 만드는 법 (운영)
릴리스할 때 Claude가 `CHANGELOG.md`의 그 절을 **사용자가 읽는 쉬운 말**로 바꿔 초안을 만들고(화면에서 무엇이 달라졌나 위주, API·운영 같은 개발자용 내용은 빼고), 관리자가 확인한 뒤 게시합니다.

## 범위 밖
- 댓글, 좋아요, 조회수, 첨부 파일, 이미지 올리기(마크다운 이미지 주소는 된다)
- 예약 게시, 이메일·푸시 알림
- 관리자 화면(회원 관리, 신고 처리)은 "나중 후보"

## 성공 기준
- SC-1 방문자가 첫 화면에서 두 번 이내로 눌러 최신 업데이트 소식을 읽는다.
- SC-2 관리자가 업데이트 글 하나를 3분 안에 게시한다 (사람이 재기).
- SC-3 관리자가 아닌 사람은 어떤 경로로도 공지사항을 쓰거나 고치거나 지울 수 없다 (테스트로 확인).
