# 테스트 전략

> 2026-10-15 정함 (사용자, 강의 "테스트 전략과 품질 관리"). 상태: **확정**(도구·규칙), **가안**(비율 목표·E2E 시점).
> 한 줄 요약: **AI가 짠 코드를 믿지 말고 테스트를 믿는다.** 테스트를 먼저 정하고, 그걸 통과하게 만들고, 정적 분석과 CI가 매번 자동으로 확인한다.

## 1. 쉬운 설명

- **테스트**는 "이 기능은 이렇게 동작해야 한다"를 코드로 적어 둔 것입니다. 한 번 적어 두면 버튼 한 번에 수백 개를 다시 확인합니다.
- 모든 테스트는 **준비(Given) → 실행(When) → 확인(Then)** 세 단계입니다. 우리 명세(`specs/*/spec.md`)의 시나리오가 이미 이 모양이라, 시나리오 번호가 곧 테스트 이름이 됩니다(예: `S6_10_50자를_넘으면_400이고_50자는_된다`).
- 입력값은 세 종류를 꼭 넣습니다.

| 종류 | 뜻 | 예 (검색어 2~50자) |
|---|---|---|
| 정상값 | 평범한 값 | `여행` |
| 경계값 | 규칙이 갈리는 바로 그 값. **버그가 가장 많이 나는 곳** | 1자, 2자, 50자, 51자 |
| 예외값 | 들어오면 안 되는 값 | 빈 값, 공백만, 이모지 반쪽 |

## 2. 도구 (확정)

| 어디 | 무엇으로 | 비고 |
|---|---|---|
| 서버 단위·통합 | JUnit 5 + AssertJ + MockMvc (`spring-boot-starter-test`) | 통합 테스트는 CI에서 진짜 PostgreSQL·Redis를 띄워 돌린다 |
| 서버 API 문서 | Spring REST Docs (`ApiDocumentationTest`) | 응답 칸이 문서와 어긋나면 실패 |
| 화면 단위·컴포넌트 | Vitest + Testing Library + MSW(가짜 서버) | 사용자가 보는 화면 기준으로 확인한다. 모르는 요청이 나가면 실패 |
| E2E | Playwright | 지금은 손으로 돌린다. 핵심 흐름 2~3개를 CI에 넣는 것은 가안 (7절) |
| 정적 분석 | SonarQube(아카데미 서버), oxlint, TypeScript | |
| 커버리지 | 서버 JaCoCo(XML), 화면 v8(lcov) | SonarQube가 둘 다 읽는다 |
| 자동 리뷰 | CodeRabbit | 지적은 맞는지 따져 보고 고치거나 답한다 |

## 3. 테스트 피라미드

단위(많이·빠르게) > 통합 > E2E(적게) 모양을 목표로 합니다. 반대 모양(아이스크림 콘)은 피합니다.

| 층 | 지금 (2026-10-15) | 목표 (가안) |
|---|---|---|
| 단위 (서버 없이) | 서버 19개 파일, 화면 6개 파일(70개) | 새 규칙은 먼저 단위 테스트로. 서비스 규칙을 조금씩 옮긴다 |
| 통합 (`@SpringBootTest`) | 59개 파일 | 화면·DB를 거치는 흐름만 |
| E2E | 0 (손으로) | 핵심 흐름 2~3개 |

지금은 통합 테스트가 두꺼운 모양입니다. 실제 DB로 돌려서 믿을 만하지만 느립니다(CI 서버 작업 약 3분).

## 5. 단계별로 언제 무엇을 돌리나

| 단계 | 돌리는 것 | 어디서 |
|---|---|---|
| push 전 (로컬) | `mvn verify`, `npm run lint && npm test && npm run build` | 개발 세션 |
| PR / develop·main push | 서버 빌드·테스트, 화면 린트·테스트·빌드, SonarQube 분석 + **Quality Gate** | GitHub Actions `ci.yml`, `sonar.yml` |
| 배포 (릴리스) | 벌마다 건강 확인 + 직접 요청(스모크), 실패하면 옛 이미지로 되돌림 | `deploy.yml`, `remote-deploy.sh` |

순서가 중요합니다: **테스트로 커버리지 리포트를 만든 뒤** 스캐너를 돌려야 커버리지가 잡힙니다. `sonar.yml`이 그 순서로 돈다.

## 6. Quality Gate (머지 조건)

- SonarQube 기본 "Sonar way": **새 코드** 커버리지 80% 이상, 중복 3% 이하, 새 이슈 0, 보안 핫스팟 모두 검토. 옛 코드가 아니라 새로 들어오는 코드에만 건다(Clean as You Code).
- `sonar.qualitygate.wait=true`: 게이트를 통과하지 못하면 "품질 분석" 체크가 실패한다.
- GitHub 브랜치 보호에서 `develop`·`main`의 필수 체크로 CI 3개(서버, 화면, 품질 분석)를 건다. **이 설정은 사용자가 GitHub 화면에서 한다.**
- 커버리지 100%가 품질 100%는 아니다. 확인(assert) 없는 테스트도 커버리지는 오른다. 숫자는 최소 기준이고 테스트의 질은 리뷰로 지킨다.

## 7. 규칙 (AI와 함께 만들 때)

1. **테스트 먼저**: 새 기능의 `tasks.md`에는 테스트 작업을 구현 작업 **앞에** 둔다. 명세 시나리오(Given-When-Then)마다 정상·경계·예외값을 정한다.
2. **실패하면 구현을 고친다**: 테스트를 바꿔 통과시키지 않는다. 테스트가 틀린 경우만 예외이고, 그 이유를 커밋 메시지에 적는다.
3. **AI가 쓴 테스트도 본다**: 확인(assert)이 없는 테스트, 구현 결과를 그대로 기대값으로 베낀 테스트를 막는다. 일부러 코드를 틀리게 바꿔 테스트가 실패하는지 확인해 본다(2026-10-15 화면 테스트에서 경계값 두 곳으로 확인함).
4. **같은 기준**: AI가 짠 코드도 같은 CI·Quality Gate·리뷰를 통과해야 merge한다.
5. **운영에서 버그가 나면**: 그 상황을 재현하는 테스트부터 더하고 고친다.
6. **놓친 경우 찾기**: AI에게 "더 필요한 테스트 케이스"를 제안받고, 넣을지는 사람이 정한다.

## 8. 앞으로 (가안)

- E2E 핵심 흐름(가입·로그인 → 글쓰기 → 읽기, 댓글) Playwright로 만들어 develop merge 뒤 또는 매일 밤 돌리기
- 화면 테스트 넓히기: 글쓰기 화면, 댓글, 블로그 관리 순서
- 서비스 규칙의 순수 단위 테스트 늘리기
