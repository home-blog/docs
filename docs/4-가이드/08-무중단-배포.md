# 08. 무중단 배포 (앱 두 벌 + 롤링)

> 2026-10-14 사용자·강사님 안내로 정함. 명세는 [`specs/011`](../../specs/011-zero-downtime-deploy/spec.md), 코드 저장소 `deploy/README.md`.

## 한 줄 요약

**같은 앱을 두 벌(a, b) 늘 같이 띄워 두고, 배포할 때 한 벌씩 바꾼다.** 한 벌을 바꾸는 동안 다른 벌이 손님을 받으니 사이트가 멈추지 않는다.

## 왜 예전에는 끊겼나

새 코드는 서버 프로그램을 새로 켜야 적용된다. Spring은 켜질 때 코드를 메모리에 올리고 부품을 조립하고 DB에 연결하는 데 수십 초가 걸린다. 예전 배포는 "옛 서버 끄기 → 새 서버 켜기"라서, 그 수십 초 동안 손님을 받을 서버가 없었다(로컬에서 재 보니 26초 동안 요청의 35%가 502).

## 비유: 은행 창구 두 개

| 우리 것 | 은행으로 치면 |
|---|---|
| 학원 Nginx | 번호표를 주고 창구로 안내하는 안내원 |
| `upstream` | 창구 목록 (1번 창구 8410 = a, 2번 창구 8411 = b) |
| 앱 a, b | 창구 두 개. 같은 일을 한다 |
| 배포 | 창구 직원 교육. 한 창구씩 닫고 교육하고 다시 연다 |

안내원은 손님을 1번, 2번에 번갈아 보낸다. 한 창구가 닫혀 있으면 그 손님을 바로 다른 창구로 안내하고, 닫힌 창구는 10초 동안 안내하지 않는다. 그래서 손님은 창구가 닫혔다는 것을 모른다.

## 학원 Nginx 설정에서 바뀐 것

```nginx
upstream geulgyeol {                                        # 창구 목록 이름
    server 127.0.0.1:8410 max_fails=1 fail_timeout=10s;     # a: 한 번 실패하면 10초 쉬게
    server 127.0.0.1:8411 max_fails=1 fail_timeout=10s;     # b
}
...
proxy_pass http://geulgyeol;                                # 포트 하나 대신 목록으로
proxy_next_upstream error timeout http_502 http_503;        # 안 되면 같은 요청을 다른 창구로
add_header X-Upstream $upstream_addr always;                # 어느 창구가 받았는지 응답에 표시
```

## 배포 한 번의 순서

| 단계 | a (8410) | b (8411) | 손님 |
|---|---|---|---|
| 평소 | 옛 버전 | 옛 버전 | 반씩 나뉨 |
| ① a의 화면 입구를 끈다 | 끄는 중 | 옛 버전 | 전부 b (Nginx가 a 대신 b로) |
| ② a를 새 버전으로 켜고 직접 확인 | 새 버전 | 옛 버전 | 전부 b |
| ③ 15초 기다린다 | 새 버전 | 옛 버전 | 다시 반씩 (잠깐 두 버전이 섞임) |
| ④ b도 같은 순서로 | 새 버전 | 새 버전 | 반씩 |

②에서 새 버전이 고장 나 있으면 a만 옛 버전으로 되돌리고 멈춘다. b는 건드리지 않았으니 사이트는 그대로다. 망가진 버전이 손님에게 가지 않는다.

③에서 15초를 기다리는 이유: 안내원은 닫혔던 창구를 10초 동안 쉬게 한다. 그보다 오래 기다려야 a를 다시 쓰기 시작한 뒤에 b를 닫는다. 둘 다 쉬는 중이면 안내할 곳이 없어 502가 난다.

## 두 버전이 잠깐 같이 돌아서 지킬 것

- **DB는 넓히고 → 좁히기**: 칸 추가는 바로 해도 된다. 칸 이름 바꾸기·지우기는 릴리스를 나눈다. 예: `nickname`을 `pen_name`으로 바꾸려면 ① `pen_name` 추가하고 둘 다 쓰기 → ② 다음 릴리스에서 `nickname` 지우기.
- **API는 v1 약속을 깨지 않는다**: 열어 둔 옛 화면이 새 서버에 요청할 수 있다. 깨지는 변경이면 `/api/v2`를 연다 ([06-API-버전과-릴리스.md](06-API-버전과-릴리스.md)).
- **로그인은 그대로**: 세션을 DB에 두어서 a로 로그인하고 b로 가도 로그인돼 있다.

## 헷갈리기 쉬운 말

| 말 | 뜻 | 우리는 |
|---|---|---|
| 이중화 | 평소에도 두 벌 이상 돌린다. 하나가 죽어도 다른 게 받는다 | ✅ 앱 두 벌 (학원 서버 한 대 안이라 "앱 이중화"까지) |
| 롤링 배포 | 여러 벌을 하나씩 차례로 바꾼다 | ✅ |
| 블루-그린 | 평소 한 벌, 배포 때 새 벌을 옆에 띄우고 한 번에 넘긴다 | 안 씀 (두 벌을 늘 두는 쪽으로) |
| 카나리 | 새 버전에 손님 일부만 보내 보고 늘린다 | 추후 후보 |
| 배포 이야기의 v1·v2 | 앱의 옛 버전·새 버전 | 우리는 릴리스 번호(0.5.1 → 0.5.2)로 부른다 |
| `/api/v1` | API 약속의 판 번호 | 배포와 상관없이 깨지는 변경 때만 올린다 |

## 트래픽 보기

```bash
for i in $(seq 10); do curl -s -o /dev/null -D - https://geulgyeol.java21.net/api/v1/auth/csrf | grep -iE 'x-upstream|x-instance'; done
```
`8410`(a)과 `8411`(b)이 번갈아 나오면 나뉘는 것이다. `8411, 8410`처럼 두 개가 찍히면 8411이 안 돼서 8410으로 다시 보낸 것이다(손님은 성공).

## 로컬에서 잰 결과 (1초에 70번쯤 요청을 보내며 배포)

| 경우 | 요청 | 실패 |
|---|---|---|
| 예전 방식 (끄고 켜기) | 4,925 | 1,700 (26초 동안 502) |
| 두 벌로 처음 넘어가기 | 11,248 | 0 |
| 롤링 배포 | 11,277 | 2 (벌을 끄는 순간 이미 보낸 POST) |
| 고장 난 버전 배포 | 3,780 | 0 (자동으로 되돌림) |

남은 2개는 Docker의 포트 중계가 꺼지는 0.1초 사이에 받은 POST다. Nginx는 글 저장 같은 POST를 두 번 저장되지 않게 다시 보내지 않아서 생긴다. GET은 모두 다른 벌로 다시 보내져 성공했다.
